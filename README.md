# Soulrend Wiki

A static wiki for the Soulrend modpack. Pages are Markdown files; a Node build script turns them into plain HTML, CSS and JS in `dist/`, which any static host can serve.

```sh
npm install          # once
npm run dev          # preview at http://localhost:4321, rebuilds and reloads on save
npm run build        # production build into dist/ (fails on any error)
npm run sync-game    # refresh game-data/ from the modpack instance
npm run font         # rebuild the pixel font from tools/font/glyphs.txt
npm run models       # rebuild the mob 3D models in assets/models/ from the modpack instance
npm run mods         # refresh the mod filters' CurseForge data (needs CURSEFORGE_API_KEY in .env)
```

`npm run dev` also prints an address you can open on a phone on the same Wi-Fi. Build errors show up in the terminal (as `file:line`, clickable in VS Code) and as a red box on the page.

## Folders

| Folder | What's in it |
| --- | --- |
| `content/` | Pages. `content/items/soul_blade.md` becomes `/items/soul_blade/`. Files or folders starting with `_` are drafts: built by `npm run dev`, skipped by `npm run build`. |
| `assets/` | Images, models and the logo, referenced from pages. `assets/models/` is generated by `npm run models`. `_` folders here are dev-only too. |
| `site/site.json` | Site title, sidebar, layout sizes, default style. |
| `site/themes/` | Styles (colour tokens for light and dark, fonts, optional extra CSS). |
| `site/stations/` | Recipe diagram layouts (crafting table, furnace, …). |
| `site/schemas/` | JSON Schemas. VS Code uses them for autocomplete in the JSON files above. |
| `game-data/` | Item names, icons, recipes and tags from the modpack (written by `npm run sync-game`), and the list of mob models (`mobs.json`, written by `npm run models`). |
| `dev-tools/` | Standalone tools served at `/dev-tools/`, copied into the build as they are, separate from the wiki. |
| `src/` | The renderer (`render/`), browser scripts (`client/`), styles and the generated font. |
| `tools/` | Build, dev server, game-data sync, font converter, and the in-game KubeJS export scripts. |
| `docs/` | Notes for editors. [`docs/style-guide.md`](docs/style-guide.md) is how to write a page (voice, sources, templates). [`docs/instance-guide.md`](docs/instance-guide.md) says where to find quests, origins, skill trees, bosses and pack mechanics in the modpack instance. |

## Reporting bugs

When you notice a bug in the modpack (a broken recipe, a crash, a mob or item misbehaving), add it to [`content/bugs.md`](content/bugs.md), the **Known Bugs** page in the sidebar. Use the entry template in that file: what happens, where and when it was seen, and any workaround. Move entries to "Fixed" once they're resolved.

## Writing a page

This section covers the syntax. For voice, naming, where numbers come from and a template for each page type, read [`docs/style-guide.md`](docs/style-guide.md).

```md
---
{
  "title": "Arcane Essence",
  "category": "Items",
  "aliases": ["Essence"],
  "items": ["irons_spellbooks:arcane_essence"],
  "summary": "A magical crafting material.",
  "infobox": {
    "item": "irons_spellbooks:arcane_essence",
    "rows": [["Type", "Material"], { "heading": "Used in" }, ["Blocks", "[[Inscription Table]]"]]
  }
}
---
**Arcane Essence** is used in [[Inscription Table|inscription tables]].

{{uses irons_spellbooks:arcane_essence}}
```

The header between the `---` lines is strict JSON (no comments, no trailing commas). Only `title` is required.

| Field | Meaning |
| --- | --- |
| `title` | Page title. Also what `[[links]]` match. |
| `navTitle` | Shorter title for the sidebar. |
| `category` | Puts the page in sidebar sections that list this category. |
| `order` | Sort position within its category (lowest first). |
| `aliases` | Other names that links and search accept. |
| `items` | Item ids this page covers. Every `[[item:…]]` and recipe slot for these items links here. |
| `icon` | Item whose icon represents the page (sidebar, search, link previews). Defaults to the first of `items`. |
| `summary` | Shown in search results and link previews. |
| `hidden` | Build the page but leave it out of the sidebar and search. |
| `infobox` | `title`, `item` (big icon), `image`, `model` (3D: a `.glb` path or a mob id such as `"cataclysm:ignis"`, or a list of ids for a page about several mobs), `caption`, and `rows` of `["Label", "markdown"]` or `{ "heading": "…" }`. The mod name and item id are added automatically; `"itemRows": false` leaves them out (for quest pages, which only borrow the icon). |

### Links and items

| Syntax | Result |
| --- | --- |
| `[[Getting Started]]` | Link by title or alias (case-insensitive). |
| `[[guides/getting-started\|the guide]]` | Link by path, with custom text. |
| `[[Getting Started#Learning magic]]`, `[[#Usage]]` | Link to a section. |
| `[[item:minecraft:diamond]]` | Icon, name and tooltip, linked to the page that lists the item in `items`. |
| `[link](/assets/maps/world.png)` | Paths starting with `/` are site-relative. |

Broken links fail the production build.

### Callouts

```md
> [!NOTE]
> Also TIP, IMPORTANT, WARNING, CAUTION, and LORE (an in-world quote).

> [!WARNING] Custom title
> Text after the marker replaces the title.
```

### Embeds

Write embeds on a line of their own, as a one-line shortcode or a fenced JSON block. The two forms are equivalent.

```md
{{recipes minecraft:torch}}

    ```recipe
    { "id": "minecraft:torch" }
    ```
```

| Embed | Example | Notes |
| --- | --- | --- |
| `recipes` | `{{recipes minecraft:torch limit=6}}` | Every recipe that makes the item. |
| `uses` | `{{uses minecraft:diamond limit=6}}` | Every recipe that uses the item. |
| | `{{recipes output=minecraft:torch input=minecraft:charcoal}}` | `recipes` and `uses` both take `output=` and `input=`; given both, only recipes matching both are shown. |
| `recipe` | `{{recipe minecraft:netherite_sword_smithing}}` | One exported recipe by id, or a hand-written one (below). |
| `items` | `{{items minecraft:diamond minecraft:emerald}}`, `{{items tag=minecraft:planks}}` | A grid of items with tooltips. |
| `image` | `{{image mobs/wraith.png caption="A wraith" align=right width=240 pixelated=true}}` | Path under `assets/`. |
| `model` | `{{model cataclysm:ignis}}`, `{{model ba_bt:land_golem ba_bt:sky_golem labels="Bahryn'muul\|Veyhz'kriin"}}`, `{{model mobs/wraith.glb animation=idle poster=mobs/wraith.png}}` | 3D viewer (see below). Mob ids come from `game-data/mobs.json`; several models share one viewer with a button each. |
| `moveset` | `{{moveset minecraft:iron_sword}}`, `{{moveset type=epicfight:longsword}}` | The item's Epic Fight moveset from `game-data/movesets.json`: per style, its combo, dash and jump attacks and innate skill, then what each skill does. With `type=`, a weapon type without a particular item. |
| `skilltree` | `{{skilltree warrior}}`, `{{skilltree warrior focus="warrior_6, warrior_80"}}` | A pannable, zoomable map of a passive skill tree from `game-data/skilltrees.json`, drawn like the game's own screen, with the game's tooltips on hover. `focus` lists node ids to light up (the rest is darkened) and the view opens on them. An ordinary node stands for its whole branch; a root, subclass, school or keystone node (one with a limited tag) stands for itself. `height=` sets the height in px (default 440); `caption=` adds a caption. |

Hand-written recipes use any station in `site/stations/`. `#tag` ingredients cycle through the tag's items.

```recipe
{ "station": "crafting_table", "grid": ["P P", "PSP", " P "],
  "key": { "P": "#minecraft:planks", "S": "minecraft:stick" }, "output": "minecraft:chest", "count": 2 }
```

```recipe
{ "station": "crafting_table", "ingredients": ["minecraft:stick", "#minecraft:coals"], "output": "minecraft:torch", "count": 4 }
```

```recipe
{ "station": "cutting_board", "label": "Spellbinding", "inputs": ["minecraft:book", "#forge:gems"],
  "outputs": [{ "item": "minecraft:enchanted_book" }], "info": "Costs **5** levels" }
```

`content/_test/kitchen-sink.md` uses every feature. Open `/_test/kitchen-sink/` in `npm run dev`.

## Styles and layout

Visitors choose a style and light/dark/system mode from the palette button. Their choice is remembered.

- `site/themes/<id>.json` defines one style: `name`, `order`, `fonts` (`sans`, `serif`, `mono`, `minecraft`, or any CSS font list), shared `vars`, and the same colour tokens for `light` and `dark`. The schema lists every required token.
- An optional `site/themes/<id>.css` adds style-specific CSS. It is scoped to that style automatically, so plain selectors like `.infobox { … }` are safe.
- Sidebar sections, layout sizes and the mobile breakpoint are in `site/site.json`.

## Recipe stations

A station is a diagram layout in Minecraft GUI pixels (slots are 18×18, drawn at 2×). Its `recipes` map says which recipe types it shows and which adapter reads them:

```json
{
  "label": "Crafting Table", "icon": "minecraft:crafting_table",
  "size": [120, 54],
  "inputs": [{ "at": [0, 0], "grid": [3, 3] }],
  "outputs": [{ "at": [94, 14], "large": true }],
  "decorations": [{ "type": "arrow", "at": [62, 19] }],
  "recipes": { "minecraft:crafting_shaped": "shaped", "minecraft:crafting_shapeless": "shapeless" }
}
```

The adapters are `shaped`, `shapeless`, `cooking`, `single`, `smithing`, `pair` (base + addition, no template) and `generic`, all in `src/render/recipes/adapters/index.js`. If a mod's recipe format matches one of them, map its type in a station. For a mod with an unusual format, add a small adapter function there.

Use `"flow": true` instead of `size`/`inputs`/`outputs` for an automatic row layout. Recipe types no station claims are still shown with the generic row layout, labelled from the type name.

## Game data

`npm run sync-game` reads the instance at `~/Documents/curseforge/minecraft/Instances/Soulrend-Development` (override with `--instance <dir>`) and writes `game-data/`. It combines three sources, later ones winning:

1. **Jar scan** (automatic). Item names, flat icons, recipes and tags straight from the mod jars. This works without starting the game, but it misses KubeJS recipe changes, tooltips, rarities and 3D block icons.
2. **In-game export** (exact data). To set it up:
   1. Run `npm run install-kubejs`. It copies `tools/kubejs/server_scripts/wiki_export.js` and `tools/kubejs/client_scripts/wiki_export.js` into the instance's `kubejs/` folders, replacing the old copies (`--instance <dir>` for another instance). Run it again after changing either script.
   2. Create `kubejs/exported/wiki/enabled.json` containing `{}`. Without this file the scripts do nothing, so they're harmless if they ever ship with the pack.
   3. Start the game and open a single-player world **on a fresh character with nothing equipped and no origin bonuses**. Spell values and Epic Fight styles are read with your player as the caster, so gear or origin bonuses would leak into them. On load, the server script writes `recipes.json`, `tags.json` and `loot_tables.json`. When you join, it writes `item_stats.json`, and the client script writes `items.json`, `gems.json`, `skills.json`, `spells.json`, `attributes.json`, `effects.json` and `enchantments.json`. Each step reports in chat, and a step that fails doesn't stop the others.
   4. Run `npm run sync-game`. Its `data:` line lists the extra files it copied.

   The extra files land in `game-data/` for writing pages; the build doesn't read them yet:

   | File | Holds |
   | --- | --- |
   | `item-stats.json` | Per item: attribute modifiers per equipment slot, durability, stack size, enchantability, burn time, tool tier, armor values, food, curio slots and curio attributes, Apotheosis loot category, Epic Fight weapon data (category, innate skill, damage attributes per style), spellbook slots. |
   | `gems.json` | Apotheosis gems: weight, dimensions, rarity range and the bonus lines at every rarity. |
   | `skills.json` | Epic Fight skills: name, category, resource, cost and description. |
   | `spells.json` | Iron's Spellbooks spells: school, cast type, cooldown, and per level the rarity, mana cost, cast time and info lines. |
   | `attributes.json`, `effects.json`, `enchantments.json` | Names, descriptions and basic properties. |
   | `loot-tables.json`, `loot-index.json` | Every loot table after datapack overrides, and an index from each item to the tables and pools that drop it. Global loot modifiers and drops made in code are not included. |

   Attribute amounts are the raw modifiers. Main-hand attack damage doesn't include the player's base 1, which the vanilla tooltip adds. Tooltip lines that mods only show while Shift is held can't be exported.
3. **Rendered icons** (exact inventory icons, including 3D items and Every Compat's runtime-generated blocks). Use [IconExporter](https://www.curseforge.com/minecraft/mc-mods/iconexporter), in the dev instance only:
   1. Download **IconExporter** and its required library **Cyclops Core** for Forge 1.20.1, and put both jars in the instance's `mods/` folder. The CurseForge page shows newer versions first, so open the full Files list and filter to 1.20.1.
   2. Launch the game, open any world, and run `/iconexporter export 32`. The `32` matches `iconSize` in `site.json`; without it the mod uses 64. Wait for it to finish (Escape cancels). With about 14,000 items this takes a while.
   3. The icons land in `icon-exports-x32/` next to `screenshots/` in the instance. Run `npm run sync-game`. It picks up the newest instance folder with "icon" and "export" in its name (or pass `--icons <dir>`), and its summary should show a large "rendered" count.
   4. Remove the two jars again, or keep them only in your dev copy. Re-export after adding or updating mods that add items.

   IconExporter names files like `minecraft__oak_slab.png` (`/` in item paths becomes `___`, and items with NBT data get a `__{…}` suffix). `sync-game` uses the plain icon when one exists, otherwise the item's first NBT variant (for example tools exported only as `{Damage:0}`).

   **Turn off any FPS or HUD overlay first** (for example `[fpsDisplay] mode = "OFF"` in `config/chloride-client.toml`). IconExporter captures the icons from the screen, so an overlay drawn in the top-left corner gets baked into them as a black box with a number.

   Without rendered icons, the jar scan falls back to the flat texture an item model points at. Items the game draws in 3D with code (GeckoLib weapons, banners, chests, …) and Every Compat items have no usable flat texture, so they show the magenta "missing" checkerboard until you export.

**Movesets** (`game-data/movesets.json`, read by the `moveset` embed) need no export step. `sync-game` reads them from the instance on every run:

- Weapon types registered in mod code are read from the jars' bytecode (`tools/lib/classfile.mjs`), by replaying each preset's builder calls (combos, innate skills, styles).
- Datapack weapon types and item capabilities come from the jars, from packs embedded in jars (`packs/<name>/data/…`), and from Paxi datapacks, which win.
- The in-game export's `item-stats.json` (Epic Fight category, default style and innate skill per item) settles ties and is checked against the result. `sync-game` warns about items that disagree, and stores the game's innate skill on such an item.

**Skill trees** (`game-data/skilltrees.json` and `game-data/skilltrees/`, read by the `skilltree` embed) also need no export step. `sync-game` reads the trees from the Passive Skill Tree jar and the Paxi datapacks, builds each node's tooltip with a port of the mod's tooltip code (`tools/lib/skilltree-tooltips.mjs`), and takes textures from the jars and then the Paxi resource packs (Tabla's PST-I pack replaces the node frames and connections). Each tree's node textures are packed into one sheet. Untranslated lang keys stay raw, as they do in game, and `sync-game` lists them.

Re-run the export (open a world with `enabled.json` present, then `npm run sync-game`) whenever recipes, items or tags change. If a script errors, the KubeJS log says where.

`game-data/` only covers items, recipes, tags, the export's data files, Epic Fight movesets and the skill tree maps. For everything else (quests, acts, origins, skill tree numbers, boss spawns), read the instance directly: [`docs/instance-guide.md`](docs/instance-guide.md) says where each thing lives and which files to skip.

## Font

`npm run font` rebuilds `src/fonts/soulrend-mc.woff2` from `tools/font/glyphs.txt`, an original Times-style pixel serif drawn for this wiki. Each glyph is a grid of `#` and `.` (rows 0-6 above the baseline, 7-8 for descenders); edit the grid and rerun. Accented Latin letters (Latin-1 and Latin Extended-A) are composed from a base letter and an accent mark, so only new base letters or marks need drawing. Bold, italic and bold italic files are generated from the same drawings: bold doubles each pixel one to the right, and italic slants the rows in whole-pixel steps. A glyph that doesn't survive the slant can get an `@italic` variant, drawn already slanted (see the italic section of the file). Characters the font lacks fall back to the UI font. The font is drawn on an 8px grid, so it is sharpest at 8, 16, 24 and 32 px.

## 3D models

Every boss, enemy and dragon the wiki covers has a model in `assets/models/<namespace>/<entity>.glb`, built from the modpack's own model data by `npm run models` (`tools/make-models.mjs`). Pages name them by entity id: `"model": "mowziesmobs:frostmaw"` in a mob infobox, or `{{model …}}` in the text. `game-data/mobs.json` lists every built model with its in-game name, which labels the buttons when one viewer holds several mobs. Every viewer has a fullscreen button at its bottom left (double-clicking the model does the same): it opens the whole viewer, pickers included, in an overlay over the page, and Esc closes it.

`tools/models/mobs.json` says where each mob's model lives, and the tool converts it:

| Source | Used by | How |
| --- | --- | --- |
| `"geo"` | GeckoLib and AzureLib mobs (Dungeons and Combat, Iron's Spellbooks, Soulslike Weaponry, …) | Reads the Bedrock `.geo.json`, and bakes the idle clip of `"animation"` (Molang included) into the model. |
| `"layer"` | Vanilla and most smaller mods | Runs the Java method that builds the `LayerDefinition` in a small bytecode interpreter (`tools/lib/models/jvm.mjs`). `"setup"` also runs the model's `setupAnim`, which poses spider legs or zombie arms; `"keyframes"` plays a vanilla `AnimationDefinition` (Cataclysm, Deeper Darker, Bosses Rise). |
| `"boxes"` | Citadel models (Alex's Mobs, Alex's Caves, Ice and Fire), Cataclysm, Mowzie's Mobs | Runs the model class's constructor in the interpreter and reads back its parts. |
| `"tabula"` | Ice and Fire's dragons and sea serpent | Reads the `.tbl`, and loops the walk poses. |
| `"mesh"` | Weapons of Miracles mobs | Reads the Epic Fight mesh. |

Adding a mob:

1. `node tools/models/discover.mjs <namespace>:<entity>` prints a draft entry. It follows the mod's renderer registration to the model and its texture.
2. Paste the entry into `tools/models/mobs.json` and run `npm run models -- --only <id>`.
3. Check the result in a viewer. Wrong textures (an overlay or glow map instead of the body), effect bones that dwarf the model (`"hide"`), and render layers (`"layers"`, `"attach"`) are the usual fixes; the header of `tools/make-models.mjs` lists every field.

The tool needs the instance and the Forge libraries from the CurseForge install (the SRG client jar and the mappings that turn `m_171599_` into `addOrReplaceChild`). The `.glb` files are committed, so the site builds without them.

Other models can be exported from Blockbench as glTF (`File → Export → Export glTF Model`, binary `.glb`), put in `assets/`, and embedded with `{{model path.glb}}`. three.js only downloads on pages that have a model.

## Dev tools

`dev-tools/` holds standalone pages served at `/dev-tools/`. The build copies them as they are, so they don't use the wiki's layout, sidebar or search.

**Mod filters** (`/dev-tools/mods/?c=<category>`, listed on `/dev-tools/`) cover CurseForge's Minecraft mods, one page per CurseForge category (World Gen, Biomes, Addons, Create, Magic, …). Each one filters by version, loader, other tags and the mod a mod depends on, which is how you find, say, every Create addon. Mods can be marked Keep or Reject, and the marks are shared across categories. Load a `minecraftinstance.json` or a modpack's `manifest.json` to check mods against that pack. The page flags declared incompatibilities and missing required mods, counting kept mods as part of the pack.

The data is `dev-tools/mods/data/<category>.json` plus `index.json`, written by `npm run mods` (`tools/curseforge-mods.mjs`). The script needs a CurseForge API key in a `.env` file (`CURSEFORGE_API_KEY='…'`, git-ignored). The first run scans every CurseForge project id, which takes about half an hour, and caches every Minecraft mod in `.cache/curseforge-mods.json` (git-ignored). Later runs refresh the cached mods and scan only new ids. `-- --full` rescans everything, and `-- --write` only rewrites the data files from the cache. Mods under 1,000 downloads are left out of the data files.

## Deploying

Upload the contents of `dist/` to any static host (GitHub Pages, Cloudflare Pages, Netlify, …). Links are relative, so the site also works from a sub-folder. Once the address is known, set `"url"` in `site/site.json` (for example `"https://wiki.example.com/"`). That adds `sitemap.xml`, canonical links and icon images for Discord link previews.
